# Sextant

**A personal research and intelligence agent you talk to on Telegram.**

A sextant fixes your position by taking readings from several independent reference points.
This bot does the same for decisions: it takes your question, your standing objectives and any
images you send, reads multiple independent sources on the open web, weighs them, and reports
what the evidence means for you: opportunities, risks, competitors and next steps.

It is one small Python process and one SQLite file. No dashboard, no vector database, no agent
framework, no paid infrastructure required.

## 1. What it does

| Area | Behaviour |
|---|---|
| **Research** | Multi-stage: understand → decompose into queries → search several providers → read pages → extract evidence → check gaps → search again → write. Bounded by hard budgets at every step. |
| **Context** | Remembers objectives, interests, projects, geography, preferences and constraints. Pulls in only what is relevant to each request. Every report states which context was used. |
| **Images** | Photos and image files are read by a vision model (text, organisations, products, contacts, figures, leads). What is in the image drives the actual search queries. Several images are combined. |
| **Reports** | Twelve-section intelligence report with citations `[S1]`. The source list and the evidence statistics are generated by code from what was actually fetched, never by the model. |
| **No duplicates** | Telegram update IDs, a request fingerprint, a unique database index and an owner-checked state machine make it impossible to generate the same research twice by accident. |
| **History** | `/history`, `/recent`, `/view` read SQLite directly. No AI call, ever. |
| **Reliability** | Provider fallback, rate-limit backoff, per-task and per-day budgets, crash recovery, graceful shutdown, authorised users only. |
| **Automation** | Optional daily research at a time you choose (default timezone `Africa/Lagos`), in-process or via GitHub Actions. Off by default. |

## 2. Verification status

Read this before relying on it.

**Verified in the build environment (78 automated tests, all passing):**

- The whole application runs end to end through the real `python-telegram-bot` library against
  a local stand-in for the Telegram Bot API: commands, inline buttons, photo download, albums,
  report delivery, restart, duplicate updates, unauthorised users.
- Research pipeline, context retrieval, image pipeline, duplicate prevention, crash recovery,
  scheduling, provider fallback, rate-limit handling, budgets, HTML extraction, SSRF and
  robots.txt protection.
- The request and response formats for Gemini, OpenAI-compatible APIs, Brave, Wikipedia and
  DuckDuckGo HTML, against mocked HTTP responses written from their documented formats.

**Not verified live:** the sandbox this was built in had no access to Telegram, Google, Groq,
OpenRouter or any search engine. So no real model has written a real report through this code
yet, and real-world search quality is untested. The model, the search engine and web pages were
simulated in tests.

**That is why `python -m sextant.doctor` exists.** After you add your keys it makes one small
real request to every configured service from your machine and prints PASS or FAIL for each. Run
it first. The most likely thing to need a change is a model name (they are renamed frequently);
that is a one-line edit in `.env`.

## 3. Quick start

Requires Python 3.11 or newer.

```bash
git clone <your-repo-url> sextant && cd sextant
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                   # then fill in the three required values
python -m sextant.doctor                               # checks every key and provider for real
python -m sextant                                      # starts the bot (long polling)
```

The three required values are `TELEGRAM_BOT_TOKEN`, `ALLOWED_USER_IDS` and one AI key
(`GEMINI_API_KEY` is the recommended first one because it also reads images).

The database is created automatically at `data/sextant.db` on first start. There is no separate
initialisation or migration step; `sextant/schema.sql` is applied idempotently on every start.

| `GROQ_API_KEY` | <https://console.groq.com/keys> | Free, text fallback. Optional. |
| `OPENROUTER_API_KEY` | <https://openrouter.ai/keys> | Free models, low daily limit. Optional. |
| `TAVILY_API_KEY` | <https://app.tavily.com> | Recommended. Makes search dependable; see below. |
| `BRAVE_API_KEY` | <https://api-dashboard.search.brave.com> | Optional. Card required. |

to work from a home connection and fail from a data centre. Add a Tavily key (free, no card at the
time of writing) for reliable results. The doctor tells you which search providers work from your
machine.

## 5. Using the bot

```
/search <question>      research (also /quick and /deep for lighter or deeper runs)
/status                 running tasks, providers, last-24h usage
/cancel [R-id]          cancel a running task
/history  /recent       previous research (from the database)
/view R-00012           open a stored report (from the database)
/setcontext [category:] text      save persistent context
/context                list it        /editcontext C12 text      /delcontext C12
/clearcontext           wipe it (asks for confirmation)
/profile                what the bot understands about you
/schedule               optional daily research
```

**Research with context**

```
/setcontext objectives: find commercial partners and clients for solar distribution
/setcontext geography: Lagos, Ogun and Abuja
/search Research the solar energy market in Nigeria
```

The plan now prioritises partners, installers, market gaps and entry barriers instead of a generic
overview, and section 12 of the report lists exactly which context entries were used.

**Research with images**

- Send a photo **with a caption**: the caption is the research question.
- Send an **album** with a caption: all photos go into one task.
- Send photos **first**, then `/search …`: staged photos are attached automatically.
- Send `/search …` and then photos within the attach window (8 s by default, extended each
  time you add something): they are attached to that task. Text sent in the window becomes
  context for that task only.
- A photo with no question is analysed and you are asked what to do with it. Research never
  starts on its own.

**Plain messages** (no command) get three buttons: research it, save as context, or ignore. This
stops an accidental message from spending your quota.

**Duplicates:** asking the same thing again shows the stored report with a *Run fresh research*
button. Fresh research is always an explicit choice.

## 6. How it works

```
Telegram ──► gate: authorised? update already seen? ──► handlers (thin)
                                                          │
                              ┌───────────────────────────┴──────────────┐
                              ▼                                          ▼
                    SQLite (single file)  ◄────────────  Runner: one task at a time,
                    tasks, reports, sources,             claim → heartbeat → complete,
                    context, images, usage,              recovery sweep every 30 s
                    caches, update IDs                              │
                                                                    ▼
                                         Pipeline: plan → search → read → extract
                                                  → gap check → (repeat) → write
                                              │            │             │
                                         AIRouter     SearchRouter    Fetcher
                                      (fallback,      (fallback,     (robots.txt,
                                       budgets)        cache)         SSRF guard)
```

```
sextant/
  config.py          environment → settings, depth presets
  schema.sql  db.py  all persistence; every query lives in db.py
  context.py         context categories, relevance retrieval, /profile
  images.py          validate, store once, analyse once
  providers/ai.py    Gemini, OpenAI-compatible (Groq/OpenRouter/Ollama/custom), OCR fallback, router
  providers/search.py  Brave, Tavily, SearXNG, DuckDuckGo, Wikipedia, OpenAlex, router + cache
  research/pipeline.py the research stages and report assembly
  research/runner.py   task state machine, deduplication, recovery
  research/fetch.py    page download and text extraction
  research/prompts.py  every prompt, in one file
  bot/app.py         Telegram handlers and delivery
  scheduler.py       optional daily research
  oneshot.py         run one scheduled research and exit (GitHub Actions / cron)
  doctor.py          live check of every configured service
```

### Research pipeline

| Stage | What happens | AI calls |
|---|---|---|
| Understand + plan | One call returns objective, entities, decision focus, 3-6 objectives and targeted queries, using the request, task context, image analyses, relevant saved context and related past research. | 1 |
| Search | Each query goes to the first working web provider; results are normalised, cached for 24 h and de-duplicated by canonical URL. | 0 |
| Read | Best candidates are opened (official and institutional domains first, at most three pages per site). Unreadable pages fall back to the search snippet, flagged as weak. | 0 |
| Extract | Sources are batched; the model returns facts, dates, quotes, source type (primary / secondary / aggregator) and the original source if the page is repeating someone else's report. | 1-3 |
| Evaluate | Code scores credibility and assigns an *origin group*. Sites repeating one press release share a group and count as one confirmation. | 0 |
| Gap check | The model judges each objective as covered / partial / missing and proposes follow-up queries, or says the evidence is sufficient. | 0-2 |
| Write | One call writes sections 1-9, a confidence assessment and the context explanation, citing `[S#]`. | 1 |
| Assemble | Code removes citations that match no source, builds the Sources section from the database, and appends computed evidence statistics and limitations. | 0 |

Depth presets are hard ceilings:

| Depth | Queries | Pages read | Rounds | AI calls | Tokens |
|---|---|---|---|---|---|
| `quick` | 4 | 5 | 1 | 5 | 60k |
| `standard` | 8 | 10 | 2 | 9 | 140k |
| `deep` | 14 | 18 | 3 | 14 | 260k |

Research stops when objectives are covered, a round adds fewer than two useful sources, or a
ceiling is reached. If it stops early the report says so in section 11.

**Honesty rules enforced in code, not just in prompts**

- No search results or no usable evidence → the task fails with an explanation. The model is
  never asked to write without evidence.
- All providers exhausted → the task fails with "nothing was generated"; no partial report is
  passed off as complete.
- The source list contains only URLs that were fetched; a test asserts the report links to
  nothing else.
- Web pages and image text are passed as untrusted data, with an instruction to ignore any
  instructions inside them.

### Context engine

Records are stored by category. For each request:

- **Framing** categories (objectives, preferences, constraints, interests, general) always apply:
  "I want partners and clients" should steer a solar-market question even though the two share
  no words.
- **Topical** categories (projects, geography, industries, image-derived) are included only when
  they share meaningful words with the request. A cocoa-export project is not injected into a
  solar question.
- A size budget caps what is sent. Priority order in every prompt: the request, then task-only
  context, then saved context (newer overrides older).
- Task-only context and image content never become persistent unless you press *Save context*.
- `/profile` separates what you stated from what is merely observed in your history, and the
  bot never adds to the stated list itself.

Retrieval is keyword overlap over SQLite rows. That is deliberate: a personal profile is a few
dozen short records, where a vector database would add cost and a dependency for no measurable
gain. If your context grows into hundreds of entries, `context.retrieve()` is the one function
to upgrade.

### Images

1. The highest-resolution version is downloaded from Telegram (size limit 10 MB).
2. The bytes are checked by signature (JPEG, PNG, WebP, GIF); the filename is not trusted.
3. The file is stored once under `data/images/<sha256>`; identical images are never stored or
   analysed twice, even when forwarded as a different Telegram file.
4. A vision model returns structured JSON: type, summary, visible text, organisations, people
   named in text, products, locations, contacts, figures, research leads.
5. That analysis is given to the planner, which builds queries around the entities. As a
   safeguard, if the plan mentions none of them, the first lead is inserted as the first query.
6. The report writer receives every image analysis and is told to relate multiple images to each
   other and flag inconsistencies.

If only the OCR fallback is available the bot says so: it can read text but cannot interpret a
chart or a scene. If no vision provider is configured, it tells you instead of guessing.

### Duplicate prevention

| Risk | Defence |
|---|---|
| Telegram redelivers an update | `telegram_updates.update_id` primary key; claimed before any work. |
| Same question sent twice while running | `UNIQUE (user_id, fingerprint) WHERE status IN ('PENDING','PROCESSING')`. The database refuses the second task. |
| Same question after completion | The stored report is offered; nothing is generated. |
| Trivial rewording ("…?" / capitals / spacing) | Fingerprint is computed on normalised text + task context + image hashes. |
| Double-tap on *Run fresh research* | Same unique index: one fresh run at a time. |
| Crash while researching | Heartbeat every 20 s. A task is re-queued only after its heartbeat is 3 minutes old, so a slow but living worker is never doubled. Two attempts, then FAILED. |
| A stalled old worker finishing late | `complete_task` succeeds only for the worker that owns the task, and inserts the report exactly once. |
| Clean restart | In-flight tasks are handed back to PENDING on shutdown and resumed on start. |
| Scheduled run fires twice | `scheduled_runs (user_id, run_date)` primary key. |

States: `PENDING → PROCESSING → COMPLETED`, or `FAILED`, or `CANCELLED`. A completed task never
changes again.

## 7. Architecture review and trade-offs

**Verdict on the proposed design:** sound. A modular monolith with SQLite and long polling is the
right size. The suggested file tree was consolidated from about 30 files to 18 because several
would have held one small function each.

**Choices**

| Decision | Chosen | Why |
|---|---|---|
| Telegram library | `python-telegram-bot` 22 | Mature, async, actively maintained. |
| Transport | Long polling | Works behind NAT, on a phone or a laptop, with no public URL or TLS certificate. |
| Database access | `sqlite3` directly, WAL mode | Nine tables do not justify an ORM. All SQL is in one file. |
| HTML parsing | `beautifulsoup4` | Small and dependable. No headless browser, so JavaScript-only pages are not readable. |
| Scheduler | A 30-second loop over a table | APScheduler would add a dependency to do less: this version also catches up after downtime and is idempotent by construction. |
| Concurrency | One research task at a time | Free tiers allow 5-15 requests per minute. Parallel tasks would only trade speed for rate-limit failures. |
| Context retrieval | Keyword overlap | See above. |

Runtime dependencies: `python-telegram-bot`, `httpx`, `beautifulsoup4`, `python-dotenv`, `tzdata`.

**Technical risks**

1. **Free model quotas are small and change without notice.** The quality of a report depends on
   the model you get for free. Mitigation: provider order with fallback, strict budgets, model
   names in `.env`, and the doctor.
2. **Free web search is the weakest link.** There is no dependable, unlimited, keyless search API.
   Mitigation: four interchangeable web providers, caching, and Wikipedia/OpenAlex as references.
3. **Many sites block bots or need JavaScript.** Mitigation: snippet fallback (flagged weak), and
   the report counts how many pages could not be opened.
4. **Model hallucination.** Mitigation: evidence-only prompts, citation validation, code-built
   source list, and a computed evidence summary. This reduces the risk; it does not remove it.
   Treat reports as a well-organised first read, and open the sources before acting on a figure.
5. **Free hosting is not guaranteed uptime.** See sections 8 to 10.

## 8. Deployment

The bot needs: Python, outbound HTTPS, about 100-150 MB of RAM, and a disk that survives restarts
(for `data/`). It does not need a public address or an open port.

**Option A: a computer you already own (true zero cost).**
A PC, an old laptop or a Raspberry Pi. Follow the quick start, then keep it running with systemd
(`deploy/sextant.service`) or Docker:

```bash
docker compose up -d --build        # data persists in ./data
```

**Option B: an Android phone with Termux.**

```bash
pkg install python git && git clone <repo> && cd sextant
pip install -r requirements.txt && cp .env.example .env && nano .env
termux-wake-lock && python -m sextant
```

Set Termux's battery mode to *Unrestricted*. On Android 12 and later the system may still kill
background processes; on Android 14+ enable *Disable child process restrictions* in Developer
Options. Some manufacturers add their own killers (see dontkillmyapp.com).

**Option C: a free cloud VM.** Google Cloud's `e2-micro` (1 GB RAM, US regions) or Oracle Cloud
Always Free. Both require a payment card for sign-up. Install as in option A with systemd.
Expect DuckDuckGo to be blocked from these IP ranges: set a Tavily or Brave key.

**Not suitable** for an always-on polling bot with a SQLite file: Render free (sleeps, no disk),
Hugging Face Spaces (sleeps, ephemeral disk), PythonAnywhere free (no always-on tasks), and
GitHub Actions (job-based; fine for the daily run only).

**Backups:** everything is in `data/`. Copy `data/sextant.db` (and `data/images/`) while the bot
is stopped, or use `sqlite3 data/sextant.db ".backup backup.db"` while it runs.

**Updating:** `git pull && pip install -r requirements.txt`, then restart. The schema is applied
on start.

## 9. Optional daily research

Nothing runs automatically unless you both enable it and give it an objective.

**Method 1: in-process (recommended if the bot is always on).**
Set `SCHEDULER_ENABLED=true`, restart, then in Telegram:

```
/schedule 05:00 Key developments, deals and policy changes in Nigeria's solar market
/schedule tz Africa/Lagos        (optional; this is the default)
/schedule off
```

A loop checks every 30 seconds. If the bot was down at 05:00 the run happens when it comes back,
provided that is within 6 hours (`SCHEDULE_CATCHUP_HOURS`); after that the day is skipped rather
than delivering "morning" research in the afternoon. Each day is a new run (it is not treated as a
duplicate of yesterday), and one day can never run twice. Daylight-saving changes are handled by
the timezone database.

**Method 2: GitHub Actions (no server at all).**
`.github/workflows/daily-research.yml` runs `python -m sextant.oneshot` each morning. Add your
keys as repository *secrets* and `SCHEDULE_OBJECTIVE` as a repository *variable*; the workflow
file explains each one. Be aware:

- GitHub starts scheduled jobs late under load, typically minutes, sometimes more. The workflow
  is set to 03:53 UTC (04:53 Lagos) to land near 5 AM. It is not exact.
- The database lives in the Actions cache, separate from any interactive bot you run elsewhere.
  Cache entries unused for 7 days are deleted (a daily job keeps it alive).
- Scheduled workflows in public repositories are disabled after 60 days without repository
  activity. Use a private repository: it keeps your logs private too. A run takes a few minutes,
  far inside the free monthly allowance.

**Method 3: system cron or Windows Task Scheduler**, on a machine that is on at 5 AM:

```
0 5 * * *  cd /opt/sextant && .venv/bin/python -m sextant.oneshot
```

`oneshot` uses the same database as the bot, so the two share history and never double-run a day.

**Method 4: no automation.** Send `/search` when you want it. The core system does not depend on
scheduling in any way.

## 11. Realistic operating cost

**Target: ₦0 / $0 per month. Achievable, with limits you should know.**

A standard research task uses about 5-8 AI requests, 6-8 search queries and 60-120k tokens.

| Setup | Monthly cost | What you get |
|---|---|---|
| Own device + Gemini free + DuckDuckGo | **$0** | Works from a home connection. Search may fail on some days. |
| Own device + Gemini free + Tavily free | **$0** | Recommended. Roughly 60 standard tasks a day by Gemini's reported Flash-Lite quota, but Tavily's 1,000 monthly credits cap you at about 4 standard tasks a day on average. |
| Free cloud VM + Gemini + Tavily | **$0** (card on file) | Same, but always on without your own hardware. |
| GitHub Actions daily run only | **$0** | One report each morning, no interactive bot. |
| Comfortable paid step-up | **about $5-10** | A paid key for a small, cheap model class plus search queries beyond the free credits. Check current prices before committing; this is an estimate, not a quote. |

**Where the limits bite first**

1. **Search credits**, not AI. Tavily's free monthly credits are the binding constraint for heavy
   use. The 24-hour search cache and page cache make retries and re-runs nearly free.
2. **Model quality.** Free Flash-Lite-class models are fast and adequate for extraction and
   structured reports but less sharp at strategic reasoning than premium models. If reports feel
   shallow, point `GEMINI_MODEL` (or `CUSTOM_AI_*`) at a stronger model: nothing else changes.
3. **Privacy.** Free tiers commonly use prompts for product improvement. For confidential work
   use a paid key or a local Ollama model.

The bot enforces its own ceilings regardless of the provider: `AI_DAILY_REQUEST_LIMIT` (400 per
provider per day), `MAX_RESEARCH_PER_HOUR` (6), and the per-task depth budgets. `/status` shows
the last 24 hours of requests and tokens per provider.

## 13. Known limitations

- Not yet run against live services (section 2). Start with `python -m sextant.doctor`.
- Pages that need JavaScript, a login or a paywall cannot be read. PDFs are skipped.
- Company registries and financial databases behind logins are out of reach; the bot reports
  what is missing rather than guessing.
- Context retrieval is keyword-based and English-oriented.
- One research task runs at a time; others queue.
- Polling means the bot must be running to receive messages. Telegram holds messages for about
  24 hours while it is offline, and they are processed once when it returns.
- The fingerprint for "same request" does not include your saved context. If you change your
  context and ask an old question, you are shown the old report and can choose *Run fresh research*.
